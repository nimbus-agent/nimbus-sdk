# Publishing the connector scaffolder — design

**Sub-project D2.** Closes ROADMAP Phase 2 box 2 (`create-nimbus-connector` scaffolding) by
publishing what D1 built. D1 (PR #95) delivered the CLI, both templates and the two scaffold
CI jobs, and deliberately published nothing; `private: true` is D2's to remove.

## The problem

`tools/create-connector` works and is exercised end to end on every CI run, and no one outside
this repository can run it. Both quickstarts open by saying so:

> `@nimbus-dev/create-connector` is `private: true` and **not published yet**, so there is no
> `npm create nimbus-connector` line to give you — it would fail.

Every reader's first instruction is therefore `git clone`, and each quickstart carries a
`cp -r` fallback whose entire justification is the unpublished state. Phase 2's exit criteria
require that "a first-time author can scaffold and ship a Python connector from the docs
alone." Cloning the SDK repository to start a connector is not that.

## What D2 changes, in one line

`npm create @nimbus-dev/connector@latest my-connector` produces a working project, and the
tarball that produces it is proven — before it is published — to generate the same tree the
checkout does.

## The name, and the exact invocation

The published name stays `@nimbus-dev/create-connector`. npm's initializer resolution is
documented as `npm init @usr/foo` → `npm exec @usr/create-foo`, so a name already inside a
scope we own is already `npm create`-shaped and needs no rename. The unscoped alternative,
`create-nimbus-connector`, buys a shorter line by re-entering the flat namespace this project
has already lost a name in — `nimbus-sdk` on PyPI belongs to an unrelated package, which is
why the Python distribution is `nimbus-dev-sdk`. A name inside a scope we own cannot be taken
from us.

The two documented invocations:

```bash
npm create @nimbus-dev/connector@latest my-connector                    # TypeScript
npm create @nimbus-dev/connector@latest my-connector -- --lang python   # Python
```

**Neither `@latest` nor `--` is decoration, and getting either wrong fails silently.**

`@latest` — npm's docs are explicit: "If you want npm to use the latest version, or another
specific version you must specify it." Without a tag npm may run a cached initializer, so an
author following a current quickstart can be running an old scaffolder.

`--` — the docs state that npm's own flags precede `--` and the initializer's arguments follow
it, illustrated as `npm init foo -- --hello` → `npm exec -- create-foo --hello`. Write
`npm create @nimbus-dev/connector@latest my-conn --lang python` and npm consumes `--lang` as its
own config. The author is following the **Python** quickstart and receives a **TypeScript**
project, with no error and no warning. That is the highest-consequence line in D2, and the
verification section below says where it is executed rather than merely asserted.

Positional arguments forward without `--`; only flags need it. The two lines above are therefore
the minimum-ceremony forms that are also correct, and they are what the quickstarts must show
verbatim.

The `bin` entry stays `create-connector`. A package with exactly one bin has it run regardless
of the bin's name, so renaming it to match the package would change nothing and would break the
`docs-excerpts.test.ts` pin for no gain.

## Python is distributed over npm, and only over npm

`--lang python` is generated by a Node CLI today, and stays generated by a Node CLI after
publication. A Python author runs the `--` form above, which needs Node 22+ **at scaffold time
only** — the generated project has no Node dependency, and neither `pyproject.toml` nor any test
in the generated tree mentions it.

The alternative — a sibling PyPI distribution exposing a `uvx`-runnable console script — was
considered and rejected. It costs a fourth publishable package, a fourth release component and a
second PyPI trusted publisher, and those are not the real cost. The real cost is that the Python
template tree would have to exist in two published artifacts at once, vendored into the sdist by
a build hook and held byte-identical to the npm copy by a new drift guard, or the two scaffolders
diverge silently and each language's authors get a different project. D2 is already adding a
publish path, a release component and a packaging guard; adding a second copy of the thing being
published is the wrong trade at this size.

The honest wart is that a Python author's first instruction names Node. It is a one-shot
invocation, it is stated plainly in `docs/quickstart-python.md` rather than buried, and it is
strictly better than today's instruction, which is to clone this repository and build a
TypeScript workspace.

## `.gitignore`, and the guard that is not about `.gitignore`

**npm strips files named `.gitignore` from published tarballs regardless of `files`.** Both
templates ship one. The moment `private` is flipped, every generated project silently loses it —
the author's first `git status` shows `node_modules/`, and their first `git add -A` may commit
it. `tools/create-connector/package.json` already records this in a `"//files"` note.

The mechanism: the file ships as **`_gitignore`** and `generate` renames it during the copy. Two
choices inside that, both deliberate.

*Why a map, not a rule.* create-vite renames any leading `_` to `.`. D2 uses an explicit
`TEMPLATE_FILE_RENAMES` map with one entry, applied to the path after name substitution. A
one-entry map is auditable and a pattern is not: the generic rule silently reinterprets the next
file someone adds whose name happens to start with an underscore, which in a Python template —
where `_private.py` is idiomatic — is a live hazard rather than a theoretical one.

*Why `_gitignore` and not bare `gitignore`.* The leading underscore tells a reader that the
on-disk name is not the final name. Bare `gitignore` reads as a mistake.

**The guard is deliberately about something larger.** The convenient invariant is "the rename
happened," and it is the wrong one — it covers exactly one filename and goes stale the moment
someone adds a second file npm treats specially. The right invariant is:

> The tarball npm would publish generates the same tree as the checkout does.

So: `npm pack` the scaffolder, extract the tarball, run the CLI **from the extracted tarball**,
and compare the generated tree against one generated from the working tree — path set and file
contents both. That catches the `.gitignore` strip, and it catches every `files` omission that
does not exist yet, which is the class of bug that "a whole-tree substitution engine renaming a
file" belongs to.

**The guard must use `npm pack`, not `bun pm pack`.** The behavior under test is npm's stripping
rule. If Bun does not reproduce it, a Bun-packed guard passes against a tarball that is not the
one the registry receives, and the guard is theatre. Whether Bun reproduces it is a question for
the implementer to answer by running both, not to assume in either direction — see STOP item 2.

**Mutation proofs, all three required before the guard is believed:**

| Mutation | Expected failure |
|---|---|
| Rename the template file back to `.gitignore` | pack-and-generate: `.gitignore` missing from the tarball-generated tree |
| Delete the `TEMPLATE_FILE_RENAMES` entry | generated tree contains `_gitignore`, not `.gitignore` |
| Remove `templates` from `files` | pack-and-generate: the tarball generates nothing |

The root `.gitignore` already covers everything both template ignore-files cover except `.env`,
so it gains that one line and the template directories stay clean when worked in place.

## Verification, and the one thing it cannot prove

The scaffold jobs change shape, and the reason is the same one D1 gave for generating outside the
repository. `scaffold-typescript` and `scaffold-python` today run
`node "$GITHUB_WORKSPACE/tools/create-connector/dist/index.js"` — the working tree. They pack the
**SDK** and install it from a tarball, precisely so no workspace link can flatter the result, and
then they run the **scaffolder** straight out of the checkout. That asymmetry is the blind spot
the `.gitignore` problem lives in, and it is not specific to `.gitignore`: no file the tarball
would omit is visible to either job.

Both jobs therefore pack the scaffolder from the commit under test and invoke the packed
artifact, via a form that also exercises npm's `--` argument forwarding. The exact form
(`npm exec --package=file:…tgz -- create-connector …` or an equivalent) is for the implementer to
establish by running it, not to copy from this document.

**What no pre-publish job can prove is the literal `npm create @nimbus-dev/connector@latest`
mapping**, because the registry has no such version until after the publish. Claiming otherwise
would be exactly the convenient-invariant substitution this design rejects elsewhere. So it moves
to where it can be true: a **post-publish smoke** in `release.yml`, after the provenance
verification, running the documented line — both of them, including the `--lang python` form —
against the real registry into a temporary directory and asserting the generated tree is the
expected language. It mirrors the existing post-publish verify jobs: install what was actually
published, and check it.

That smoke job inherits their propagation-lag lesson wholesale. `npm create` resolves a packument
and downloads a tarball; both are subject to the same lag that has already turned two good
releases red. It retries, and `--prefer-online` or its equivalent is mandatory, because npm
caches the negative packument.

## The release train

`tools/create-connector` joins the existing train as a third component rather than getting its
own:

```json
"tools/create-connector": {
  "release-type": "node",
  "component": "create-connector",
  "package-name": "@nimbus-dev/create-connector"
}
```

`sdks/typescript/scripts/release-config-guard.test.ts` already generalises to it. Its component
rule is `component === path.split("/").pop()`, which `"create-connector"` satisfies, and the
`node` release-type already has a `VERSION_READERS` entry, so no reader is added — the guard's
"a package whose release-type has no reader FAILS rather than being skipped" clause is satisfied
without touching it. `.release-please-manifest.json` gains one key; tags become
`create-connector-v*`.

**A third component makes manifest contention likelier, and that is already answered.**
`always-update: true` (PR #98) refreshes every open release PR on each run, so a third separate PR
rebases itself rather than stranding. `separate-pull-requests: false` remains forbidden: a grouped
PR takes `group-pull-request-title-pattern`, whose default omits `${version}`, and release-please
then silently skips creating the release and tag (googleapis/release-please#2712). D2 does not
touch either key, and the guard asserts both.

`release.yml` gains a `create_connector_released` output and a `publish-create-connector` job
cloned from `publish` — `harden-runner` with `egress-policy: audit`, the OIDC-and-npm-floor
preflight, `npm publish --provenance --access public` with no `NODE_AUTH_TOKEN`, the
install-and-`npm audit signatures` retry loop, and the pinned `verify-npm-provenance` action
repointed at the new package name. It binds to the **same workflow file** as the SDK's publish
job, so the new trusted publisher names `.github/workflows/release.yml` exactly as the existing
one does.

**One detail the plan must pin.** With no prior tag for this component, release-please scans
history from the beginning and would sweep D1's `feat:` commit (#95, which created the whole
directory) into the first changelog. `bootstrap-sha` is the mechanism; its exact semantics
against `last-release-sha` are for the implementer to confirm from release-please's own
documentation before choosing between them.

## Versions

The bootstrap publish is **`0.0.0`**, which is already the version on disk, and the first
release-please-cut version is **`0.1.0`**. From a `0.0.0` manifest a `feat:` lands on `0.1.0`
under release-please's pre-1.0 defaults, so neither `bump-minor-pre-major` nor
`bump-patch-for-minor-pre-major` needs setting.

`0.x` rather than `1.0.0` is the honest claim. The CLI's flag surface is not settled: `--lang`
gains a value every time Phase 3 lands a language, and that changes a documented invocation. No
author outside this repository has generated a project yet. And the Python binding this tool
scaffolds against is itself `0.4.0` — a `1.0.0` scaffolder would claim more stability than the SDK
it wires you into.

## Documentation

`docs/quickstart-typescript.md` and `docs/quickstart-python.md` are **rewritten at the top, not
patched**. Both open by naming the unpublished state as the reason for what follows, and both
carry a `cp -r` fallback whose whole justification is that state. When the state changes, the
justification is gone and the sections go with it; editing "not published yet" into "published"
leaves two documents structured around a fact that is no longer true.

`docs-excerpts.test.ts` keeps both pinned to the CLI's `USAGE` string via its `quoted-from`
marker, and `USAGE` itself changes: it reads `Usage: create-connector <name> …`, which is the
from-a-checkout invocation. It should read as the published one.

Also updated: `sdks/typescript/README.md`; `CLAUDE.md`'s scaffolder section, which currently opens
"that **publishes nothing**"; and ROADMAP box 2, which is checked, with its built-but-unpublished
annotation removed.

## STOP — decisions that are not an implementer's to improvise

**1. npm cannot publish a package's first version over OIDC.** A trusted publisher can only be
configured on a package that already exists in the registry (npm/cli#8544, open). PyPI's *pending
publisher* — which is what makes `publish-python` token-less from its very first release — has no
npm equivalent. `@nimbus-dev/sdk` never hit this because it already existed on npm when this
repository was extracted from the monorepo.

So the first `@nimbus-dev/create-connector` publish is manual and credentialed, and it is the
repository owner's step, not a task in a plan:

1. mint a temporary granular npm token scoped to the `@nimbus-dev` scope;
2. `npm publish` version `0.0.0` from a clean checkout;
3. configure the trusted publisher on npmjs.com — `nimbus-agent/nimbus-sdk`,
   `.github/workflows/release.yml`, matching the existing binding;
4. **revoke the token.**

Every release after that is token-less OIDC with provenance. The implementation plan must be
sequenced so nothing depends on this having happened until the merge that would publish, and must
say so where a reader will hit it.

**2. Whether `bun pm pack` reproduces npm's `.gitignore` stripping.** It decides whether the
packaging guard can use this repository's existing pack idiom or must reach for `npm pack`. Cheap
to answer by running both and diffing the tarball listings; expensive to get wrong, because the
wrong answer produces a guard that passes against a tarball nobody will ever install.

## Risks carried knowingly

**A published scaffolder ages in public.** Today a broken template dependency range surfaces as a
red CI job on an unrelated PR — D1 chose the fresh install for exactly that reason. After
publication it can also surface in a stranger's terminal, between our CI runs. The mitigation is
unchanged and still correct: no lockfile in the template, fresh resolution every CI run, and a
scaffolder release is now cheap to cut.

**The bootstrap `0.0.0` is permanently installable.** npm will not remove it after 72 hours.
`npm deprecate`-ing it after the trusted publisher is configured is the conventional answer and
costs nothing.

**Three separate release PRs now contend on one manifest.** `always-update` handles it, and this
design adds no new mechanism for it deliberately — the alternative is the trap the guard's comment
documents.

## Task shape

Six tasks: the `_gitignore` rename with its map and unit guards; the pack-and-generate packaging
guard, mutation-proved; the two scaffold CI jobs repointed at the packed artifact; the
release-please component with its manifest entry and `bootstrap-sha`; the `publish-create-connector`
job plus the post-publish `npm create` smoke; the documentation rewrite and ROADMAP close.

Publishable-package hygiene — removing `private: true`, adding `publishConfig.access`,
`repository`, `description`, `keywords`, `homepage`, `bugs`, and the currently-absent `README.md`
and `LICENSE` under `tools/create-connector/` — rides with the first task rather than becoming a
seventh.
