# Quickstart — a TypeScript connector

From nothing to a connector that performs the contract-version handshake and then serves
MCP tools over the same two streams. Everything below is generated by the scaffolder in
[`tools/create-connector/`](../tools/create-connector/), and CI generates, installs,
builds, tests and *drives* that same output on every run — so this page describes code
that is executed, not code that is described.

Python author? See [quickstart-python.md](./quickstart-python.md). The two connectors are
the same connector; only the host language differs.

## 1. Generate

`@nimbus-dev/create-connector` is `private: true` and **not published yet**, so there is
no `npm create nimbus-connector` line to give you — it would fail. Run it from a checkout:

```bash
git clone https://github.com/nimbus-agent/nimbus-sdk && cd nimbus-sdk
bun install
bun run --cwd tools/create-connector build
node tools/create-connector/dist/index.js weather-connector --dir ~/src/weather-connector
```

Generate **outside** the checkout, as `--dir` does above. Inside it, Node's resolution walks
up to the repository's workspace `node_modules` and satisfies `@nimbus-dev/sdk` from there —
a resolution no real author has, and one that hides a broken dependency range until someone
else hits it. The CI jobs generate into `$RUNNER_TEMP` for exactly this reason.

<!-- quoted-from: tools/create-connector/src/index.ts -->

```text
Usage: create-connector <name> [--lang ts|python] [--dir <path>]

  <name>          lowercase kebab-case, starting with a letter (e.g. weather-connector)
  --lang          ts (default) or python
  --dir           where to write it (default: ./<name>)
```

It writes 10 files and prints where they went. Exit codes: `0` on success, `1` for a
usage or validation error, `2` when the target directory already exists and is not empty
— it never writes into an occupied directory.

### The name rule, and why it is stricter than you expect

**Lowercase kebab-case, starting with a letter.** `weather-connector` is fine;
`weather_connector`, `WeatherConnector`, `2fa-connector`, `weather--connector` and
`-weather` are all refused, as is a short list of reserved words (Python keywords, `src`,
`dist`, `test`, `node_modules`, and the Windows device names `con`, `nul`, `com1`…).

One name has to serve as an **npm package name**, a **Python module name** and a
**directory name** at the same time, so the CLI takes the intersection of all three
rather than validating three times and emitting three diagnostics. That is stricter than
any single ecosystem — npm would accept `weather_connector`, Python would accept
`WeatherConnector` — and stricter than the Nimbus contract itself, which constrains
`manifest.id` only as a required non-empty string. An invalid name is rejected, never
silently rewritten: a project named something its author did not type is worse than an
error message.

### The `cp -r` fallback

The scaffolder only copies a tree and rewrites three literals out of it, so you can do
its whole job by hand:

```bash
cp -r nimbus-sdk/tools/create-connector/templates/typescript weather-connector
```

Then replace, in **file contents and in path segments**:

| Template literal | Yours |
| --- | --- |
| `nimbus-quickstart-connector` | `weather-connector` |
| `nimbus_quickstart_connector` | `weather_connector` |
| `Nimbus Quickstart Connector` | `Weather Connector` |

The TypeScript template has no name in a path segment, so a content-only pass is enough
here; the Python one does — see [quickstart-python.md](./quickstart-python.md).

## 2. Install, test, run

```bash
cd ~/src/weather-connector
npm install
npm test     # pretest = typecheck + build, then unit + acceptance tests
npm start    # node dist/main.js — the connector on stdio
```

`npm test` runs `typecheck` and `build` first, through `pretest`, because the acceptance
tests drive the built `dist/main.js` as a real process. There is no way to test a stale
`dist/`.

To see it answer for yourself — a hello it can agree with, then one it cannot:

```bash
printf '{"nimbus":"hello","contractVersions":["1"]}\n' | node dist/main.js; echo "exit=$?"
printf '{"nimbus":"hello","contractVersions":["2"]}\n' | node dist/main.js; echo "exit=$?"
```

The first answers with its own hello and exits `0`; the second exits `20`
(`CONTRACT_HANDSHAKE_EXIT`) with `handshake refused: …` on stderr. That pair is exactly
what the `scaffold-typescript` CI job asserts.

## 3. What you got

| File | What it is |
| --- | --- |
| `manifest.ts` | The manifest the gateway reads, and the tool list. **Contract.** |
| `handlers.ts` | Your logic. Imports neither SDK, so it is testable without a wire protocol. |
| `main.ts` | The only file that knows a protocol exists: handshake, then MCP. |
| `handlers.test.ts` | Unit tests for your logic. |
| `main.test.ts` | Acceptance tests for the wire behaviour. **Keep these.** |
| `package.json` | `private: true` — remove that when you actually want to publish. |
| `tsconfig.json` / `tsconfig.build.json` | Typecheck everything including tests; build sources only. |
| `README.md`, `.gitignore` | Yours to edit. |

### Contract, and yours

**Contract** — the manifest's shape, the handshake, and exit code `20` on refusal. The
gateway depends on these; changing them breaks your connector.

**Yours** — which MCP server you use, what your tools do, how you test them. The SDK has
no opinion. It ships no server: `@nimbus-dev/sdk` is a dependency-free authoring
contract, so the template brings its own `@modelcontextprotocol/sdk` and `zod`.

## 4. What to edit first

1. **`manifest.ts`** — `id`, `displayName`, `description`, `author`. `runtime: "node"`,
   `permissions` and `hitlRequired` are contract fields; change them deliberately.
2. **`handlers.ts`** — delete `echo`, write your function, test it in `handlers.test.ts`.
3. **`manifest.ts` again** — add the tool's name and description to `TOOLS`.
4. **`main.ts`** — register it next to `echo` with a Zod shape for its input.

Keep tool names free of row-data segments. A connector indexes metadata; record bodies
stay on the system they came from. `assertNoRowDataTools` from `@nimbus-dev/sdk` will
hold you to it if you add it to `handlers.test.ts`; the template does not wire it up for
you.

## 5. Read this before you restructure `main.ts`

The one non-obvious thing in the template, and the reason `main.test.ts` exists.

The gateway announces unprompted — [contract-version.md](./spec/negotiation/v1/contract-version.md)
§5 has both peers write their hello without waiting for the other — so its hello and its
**first MCP request very often arrive in the same read**. `performHandshake` copes with
that, but only if you take back what it hands you:

- the complete frames it read past the hello come back as `result.pending`;
- a frame the gateway left half-written stays inside the `NdjsonLineReader` you passed in.

<!-- excerpt-of: tools/create-connector/templates/typescript/main.ts -->

```ts
  const replay = Readable.from(
    (async function* stream(): AsyncGenerator<Uint8Array> {
      for (const frame of result.pending) {
        yield frameOf(frame);
      }
      for (;;) {
        const next = await stdinChunks.next();
        if (next.done === true) {
          break;
        }
        for (const frame of reader.push(new Uint8Array(next.value))) {
          yield frameOf(frame);
        }
      }
      for (const frame of reader.flushFrames().frames) {
        yield frameOf(frame);
      }
    })(),
    { objectMode: false },
  );

  await connectTransport(createMcpServer(), replay);
```

So `main.ts` does **not** hand `process.stdin` to the MCP transport. It builds a stream
that yields `result.pending` first and then keeps pushing the rest of stdin through the
*same* reader, and gives the transport that. `StdioServerTransport` takes a readable and
a writable, so this costs nothing.

Serving on raw `process.stdin` after the handshake loses both — silently, with no error
and no log line. The session's first request is simply never answered.

`main.test.ts` guards each half separately, because a fix for one does not fix the other:

- `answers a request pipelined into the hello's chunk` — fails if you drop the `pending`
  replay;
- `completes a frame the hello's chunk left half-written` — fails if you replay `pending`
  but then forward raw stdin chunks to the transport instead of pushing them through the
  reader.
