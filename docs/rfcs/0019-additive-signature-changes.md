# RFC-0019 — Extending a declaration is adding, not breaking

- **Status:** accepted
- **Opened:** 2026-09-01
- **Landed:** 2026-09-01
- **Affects:** [RFC-0015](./0015-tiered-stability.md) §2's `Signature changed` / `stable`
  cell, and `sdks/typescript/scripts/stability-rules.ts`, which encodes the table
- **Roadmap:** no box of its own; it unblocks additive growth of the `agents` brief types
- **Pillars:** 7 (versioning & compatibility)
- **Builds on:** [RFC-0017](./0017-battery-specifications.md) §4, which made the same
  correction to the `Export added` / `frozen` cell, on the same grounds, and established
  that an amendment supersedes one cell rather than editing RFC-0015 in place

## Summary

**Adding an optional member to an existing exported declaration costs `feat:`, not
`feat!:`.** This document supersedes one cell of RFC-0015's rule table: `Signature changed`
at `stable`, and only for the case where every change is an added optional member. Every
other signature change is untouched and still costs `feat!:`.

A new `ChangeKind`, `extended`, carries the distinction, so the rule table and the code that
encodes it stay the same shape.

## Problem

RFC-0015 §2 opens:

> The tier governs **what it costs to break something, not what it costs to add.**

Its rule table then charges `feat!:` for an addition whenever that addition happens to live
*inside* an existing declaration rather than beside it. Adding an export is `feat:`; adding
an optional field to an exported type is `feat!:` — a major — even though no consumer can
tell the difference except by gaining a field they may ignore.

That is the same internal inconsistency RFC-0017 §4 found in the `frozen` row, one cell over.

**It is not hypothetical, and the repository has already paid it once — in the other
direction.** `WhyBrief.changeSubject` (#132, 2026-08-19) added exactly this kind of optional
field and landed as a plain `feat:` minor, with the reasoning recorded in its own commit
message: *"Optional is the design, not a convenience: a brief written before the field
existed still satisfies the type, which is what keeps this a minor release rather than a
major one."*

`BREAKING_KINDS` landed six days later, on 2026-08-25, with RFC-0015. **The precedent
predates the rule.** Under today's gate that same change would demand 2.0.0, and so does its
successor: `why` is growing a third input arm and needs a third optional subject field.

Left alone, the gate charges a major for every optional field the agent briefs ever grow.
The package is at 1.30.1; the next four such additions would take it to 5.0.0 without a
single consumer breaking.

## The change

### 1. A new `ChangeKind`: `extended`

`extended` is a signature change in which the head declaration is the base declaration plus
**optional members only**. It sits beside `signature` rather than replacing it.

| Surface change | `experimental` | `stable` | `frozen` |
|---|---|---|---|
| Export added | `feat:` | `feat:` | `feat:` |
| Export **extended** (optional members only) | `feat:` | **`feat:`** | `feat:` + RFC |
| Export removed | `feat:` | `feat!:` + window | `feat!:` + window + RFC |
| Signature changed | `feat:` | `feat!:` | `feat!:` + RFC |

Only the bolded cell is new law. The `Export added` row is RFC-0017 §4's; the last two rows
are RFC-0015's, unchanged.

### 2. `frozen` is deliberately not exempted

RFC-0017 §4 exempted whole-export additions at `frozen`. This document does **not** extend
that to `extended`, and the difference is deliberate rather than an oversight: freezing a
module is a promise about its *shape*, and growing a member changes the shape a
reimplementation must match. Narrowing this correction to `stable` keeps its blast radius to
the cell the evidence covers.

### 3. Conservative by construction

The classifier (`classifyDeclarationChange`) answers `extended` only when it can prove the
change additive, and `signature` in every other case — including every case it cannot parse.
The failure mode is an over-strict bump, never an under-strict one.

Three conservatisms are load-bearing:

- **TypeScript only.** In Python and Go a signature change already reads as a removal plus
  an addition, so there is no declaration pair to compare.
- **Every base line must survive**, checked as a multiset. A removal riding along with an
  addition must not be laundered into a minor — the same per-change reasoning RFC-0017 §4
  applied to its own exemption.
- **Every added line must be an optional member.** A new required member, a retyped member,
  and a required-to-optional demotion all stay `signature`.

The comparison is line-based, which is a ceiling rather than a shortcut: the goldens are
generated by `api-surface.ts` from `dist/*.d.ts`, so one member per line is a property of
the emitter. Parsing TypeScript here would put a second, subtly different type model inside
the release gate — the thing most likely to disagree with the compiler exactly when it
matters.

## Compatibility

No consumer-visible change. This alters what the release gate *demands*, not what the
package *ships*. Existing published versions are unaffected, and no previously-accepted bump
becomes retroactively wrong.

## Alternatives rejected

**Ship the majors.** Honest, and what the gate demands today — but it prices additive growth
of a brief at a major each, which is precisely what RFC-0015 §2 says a tier is not for. The
version number would stop carrying information: a 2.0.0 that breaks nothing teaches
consumers to ignore majors.

**Widen the exemption to `frozen` as well.** Symmetric with RFC-0017 §4 and tempting for
that reason, but freezing is a promise about shape and there is no evidence yet that a frozen
module needs to grow. Deferred rather than refused: if one does, that is its own RFC with a
real case attached.

**Parse TypeScript in the gate.** Strictly more precise, and strictly worse: a second type
model in the release path that can disagree with `tsc`. The line-based classifier is
deliberately dumber and fails closed.

**Let authors override the gate per PR.** An escape hatch turns the gate into a suggestion,
and the one thing a release gate must not be is optional.
