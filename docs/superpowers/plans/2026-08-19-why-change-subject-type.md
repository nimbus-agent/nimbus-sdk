# `WhyChangeSubject` — the pull-request subject a why brief can carry

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an optional `changeSubject` to `WhyBrief`, so a `why` brief can name the pull request it is about instead of a file path — without breaking any existing consumer.

**Architecture:** Two type edits and one export. `WhyChangeSubject` is a leaf shape and joins `WhySubject` in `agents/brief-types.ts`; `WhyBrief` in `agents/brief-composites.ts` gains an **optional** field referencing it. Optionality is the whole design: it keeps the release a minor, and it is proven by a test that constructs a `WhyBrief` without the new field and requires it to compile.

**Tech Stack:** TypeScript (strict), Bun test, Biome, release-please. Package `@nimbus-dev/sdk`, currently `1.17.0`.

**Spec:** `docs/superpowers/specs/2026-08-19-why-from-a-pull-request-design.md` §1.1 — **in the `nimbus-web-clipper` repo** (`C:/gitrep/nimbus-web-clipper`, branch `worktree-c2-4-why-from-a-pr`). This SDK change is step 1 of that spec's three-repo chain (§6); nothing here consumes the field yet.

## Global Constraints

- **Additive and optional only.** `WhySubject` must not change. Any edit that could break a consumer reading `subject` is out of scope — it would turn a minor release into a major.
- **The Python binding is not touched.** It carries `ipc`/negotiation only and does not mirror brief types.
- **No runtime dependency may be added** to the published surface (`CLAUDE.md`: "if a helper, inline it").
- **Conventional Commits are enforced** (`scripts/conventional-commit.test.ts`) and drive release-please. The feature commit must be `feat(agents): …`. Any non-empty scope parses — `SUBJECT = /^([a-z]+)(?:\(([^()]+)\))?(!)?: (.+)$/` — so `(agents)` is a choice, not a requirement.
- **The pull request title must declare at least the highest impact it carries.** This repo squashes, so the aggregate subject is the only thing release-please sees. This PR carries a `feat` and a `docs`, so its title stays `feat:` — retitling it `docs:` because the diff looks documentation-heavy would ship a new public export as a patch, which is precisely the failure `conventional-commit.ts` was written after (`sdk 1.9.0`). Over-declaring is allowed; under-declaring loses semver.
- **`CHANGELOG.md` is generated by release-please — never hand-edit it.**
- **`bun run build` must run before `bun test`**: `scripts/docs-coverage.test.ts` asserts `dist/index.d.ts` exists and fails with "run `bun run build` before `bun test`" otherwise.
- All commands run from the repo root unless stated.

- [ ] **Step 1: Write the failing test**

Create `sdks/typescript/src/agents/brief-composites.test.ts`:

```ts
import { describe, expect, test } from "bun:test";
import type { WhyBrief } from "./brief-composites.js";
import { isWhyBrief } from "./brief-guards.js";
import type { WhyChangeSubject } from "./brief-types.js";

const base = { agentVersion: 1 as const, generatedAt: 1, latencyMs: 1, gaps: [] };

/**
 * The non-breaking claim, enforced rather than asserted: a `WhyBrief` written
 * before `changeSubject` existed must still satisfy the type. If this file ever
 * stops compiling, the field stopped being optional and the release stopped
 * being a minor.
 */
const legacy: WhyBrief = {
  ...base,
  kind: "why",
  query: { ref: "src/a.ts", line: 12 },
  subject: { repoRoot: "/repo", filePath: "src/a.ts", lineNo: 12, symbol: null },
  findings: [],
};

const changeSubject: WhyChangeSubject = {
  itemId: "github:acme/web#482",
  entityId: "ent_1",
  repo: "acme/web",
  number: 482,
  url: "https://github.com/acme/web/pull/482",
  title: "Cache the resolver",
  modifiedAt: 1_700_000_000_000,
};

const fromPr: WhyBrief = {
  ...base,
  kind: "why",
  query: { ref: "https://github.com/acme/web/pull/482", line: null },
  subject: null,
  changeSubject,
  findings: [],
};

describe("WhyBrief.changeSubject", () => {
  test("a brief written without it is still a WhyBrief", () => {
    expect(legacy.changeSubject).toBeUndefined();
    expect(isWhyBrief(legacy)).toBe(true);
  });

  test("a brief carrying it is still a WhyBrief", () => {
    expect(isWhyBrief(fromPr)).toBe(true);
  });

  /**
   * `isWhyBrief` checks the wire shape (`kind`, `agentVersion`, `gaps`,
   * `generatedAt`, `latencyMs`, `query`, and `findings` being an array). An
   * optional field needs no guard clause, and adding one would reject the
   * legacy brief above. Pinned so a future edit to `brief-guards.ts` has to
   * argue with a test rather than with a comment.
   */
  test("the guard does not require the new field", () => {
    const { changeSubject: _dropped, ...withoutIt } = fromPr;
    expect(isWhyBrief(withoutIt)).toBe(true);
  });

  test("null is distinguishable from absent", () => {
    const explicitlyNone: WhyBrief = { ...legacy, changeSubject: null };
    expect(explicitlyNone.changeSubject).toBeNull();
    expect(isWhyBrief(explicitlyNone)).toBe(true);
  });

  /**
   * A DIFFERENT axis from the test above: that one is about `changeSubject`
   * itself being null versus absent; this one is about its members being null.
   * `number` and `modifiedAt` are `number | null` because a connector may index
   * a pull request without either, and null must survive the round trip as a
   * value rather than being confused with an omitted field.
   */
  test("nullable members accept null", () => {
    const sparse: WhyChangeSubject = {
      ...changeSubject,
      number: null,
      modifiedAt: null,
    };
    const brief: WhyBrief = { ...fromPr, changeSubject: sparse };
    expect(brief.changeSubject?.number).toBeNull();
    expect(brief.changeSubject?.modifiedAt).toBeNull();
    expect("number" in sparse).toBe(true);
    expect(isWhyBrief(brief)).toBe(true);
  });
});
```

In `sdks/typescript/src/agents/brief-types.ts`, directly after the `WhySubject` block (currently ending at line 108), add:

```ts
/**
 * The subject of a `why` brief asked about a whole change rather than a line.
 *
 * Present only when the caller supplied `prUrl`; `WhySubject` (a file, a line, a
 * symbol) is untouched and remains what a `ref`-shaped call resolves to. The two
 * are alternatives, not a union: `subject` is null on this arm, and a consumer
 * that never sends `prUrl` never receives a brief carrying this field.
 */
export type WhyChangeSubject = {
  /** Index item primary key — `"<service>:<repo>#<number>"`, e.g. `"github:acme/web#482"`. */
  itemId: string;
  /** `graph_entity.id` of the `pr` entity the lanes were answered from. */
  entityId: string;
  /** `"acme/web"` — the repo path as the connector indexed it. */
  repo: string;
  /** Null when the indexed item carried no number (a forge or connector that omits it). */
  number: number | null;
  url: string;
  title: string;
  /** Epoch ms, as the source reports it. Null when the item carried none. */
  modifiedAt: number | null;
};
```

**Type consistency:** `WhyChangeSubject`'s seven members are written identically in the test fixture (Task 1 Step 1), the declaration (Step 3) and the spec. `changeSubject` is spelled the same in all five places it appears.

**Review response (2026-08-19):** the plan review asked for null coverage on `number`/`modifiedAt` — added as its own test rather than folded into "null is distinguishable from absent", since that one is about the field being null versus absent and this one is about its members. It also asked whether `changeSubject` needs a runtime sub-shape guard: no, and the review agreed — `createBriefGuard` is base shape plus one predicate, and every guard here is shallow. Pinning that a malformed `changeSubject` is *accepted* was considered and declined; it would enshrine permissiveness and block a later tightening. The scope question checked out (`(agents)` parses), and reading that guard added the aggregate-impact constraint above, which the plan had been missing.

**Out of scope, deliberately:** the gateway's `requireWhyParams`, the resolver, the lanes and the render branch are all steps 2-3 of the spec's chain and live in the Nimbus repo. This plan ends at a published type.
